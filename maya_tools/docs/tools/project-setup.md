# Mindmeld: Project Setup

## What it does
Mindmeld (window title; the code and file names stay "project setup" throughout) is the authoring UI over the two JSON files every FabricatorStudio project runs on: `session.json` (units, frame rate, playback range, undo depth, camera clips, grid, blueprints subpath) and `export_mapping.json` (per-asset-class source/destination path rules, prefixes, FBX export presets, library subpaths, engine up axis) — the shareable *project truth*, carrying no machine-absolute paths. Your machine's Source Art Root, Content Root, and any absolute overrides live separately in `fabricator_project_configs/_user/<slug>.json`, per user. The project pairs live under `<maya folder>/fabricator_project_configs/<slug>/`, one folder per project, outside the repo/install tree, so a checkout or uninstall can never destroy an artist's authored configs. The tool holds one in-memory "authored" dict per project; `config_generator.py` compiles the friendly `asset_classes` model (which folders hold which asset type, using `{name}`/`{path}` placeholders) down into the exporter's raw `path_patterns` regex on every save, and `config_validation.py` is the sole gate that runs before any write, blocking on errors and confirming-through on warnings.

## Quick start
1. Open Mindmeld from the FabricatorStudio menu's **Project Setup** entry, or the same-named button on the `fsModel` shelf - both now open this same manager.
2. Click **New**, pick an **Engine** template (Unreal5 ships fully vetted; Unity and Godot ship with complete starter asset classes and FBX presets but are currently marked experimental pending Adrian's manual export/import round-trip in each engine; Generic is an explicit, empty DIY starter), then type a **Name** - the folder-slug preview below it shows exactly what identity folder will be created.
3. Browse to your **Source Art Root** (where this machine keeps the source art tree) and **Content Root** (where exports land, e.g. the engine content dir), fill in the **Asset Classes** table (id, label, export types, source dir, dest dir, anim gameplay/cinematic dest), and watch the **VALIDATION** panel at the bottom; **Save** stays disabled while any error is listed.
4. Click **Save**. It writes `session.json` + `export_mapping.json` atomically to `fabricator_project_configs/<slug>/` (never overwriting an existing folder on create), then offers a scaffold checklist of the directories your config implies - check only the ones you want created on disk right now.
5. Back on the project list, select the project and click **Apply & Activate** to apply the session settings to the current Maya session and mark it the active project for the toolbar/blueprint library in one action.

## Workflow
A project config is exactly two files under `fabricator_project_configs/<slug>/` (`<maya folder>` = `MAYA_APP_DIR` if set, else the redirect-aware real Documents folder's `maya` subfolder - not a stale `~/Documents` copy). `slug` is the project's real identity: it is the lowercased, `[a-z0-9_]`-safe form of the Name field, computed the same way everywhere (`project_config_io.slugify`), and it never changes on its own - renaming a project to a name whose slug differs is rejected outright ("would move the identity folder... use Duplicate... then delete... if no longer needed"), so Edit can never orphan a second folder. Studios on Perforce or a network share point `FABRICATOR_PROJECT_CONFIGS` at a shared root before Maya launches; every consumer (this tool, the exporter, the blueprint library, `maya_startup`) funnels through the same `configs_dir()` so one env var redirects them all, while per-user state (active project, window/dock prefs) stays local under `maya_root()` regardless.

**Engine templates** live in-repo under `framework/project_configs/_<engine>/` ('`_`'-prefixed = template, never a live project) and are copied to each artist's local configs folder on first touch, without ever overwriting a config that's already there. Picking a template on **New** seeds session defaults, a complete `fbx_presets` triple (static_mesh / skeletal_mesh / animation, with the correct `FBXExportUpAxis` per engine), the engine bone-space up axis (`engine_up_axis: "z"` on the Unreal templates - the root-frame conversion that keeps engine animations from playing characters pitched 90 degrees), and starter asset classes; **Engine locks once a project exists** - Edit can't change it. Each template's own `export_mapping.json` carries an `"_status"` field once it is not yet vetted: `_unreal5` currently has none (it is the one template Adrian has run a real export/import round-trip against, per the design spec's template gate); `_unity` and `_godot` both carry `"_status": "experimental"` even though their `asset_classes`/`fbx_presets` are already complete and validate clean, because that manual per-engine round-trip hasn't been recorded yet; `_generic` also carries `"_status": "experimental"` and additionally ships with `asset_classes: []` and empty `fbx_presets` for each type - it needs its own asset classes and FBX presets authored before it will validate clean at all, since `fbx_presets.<type>` being empty is a hard save-blocking error for every project regardless of template.

**Asset Classes** is the core authoring surface: each row's `source_dir` (relative to your **Source Art Root**, using `{name}` for one path segment or `{path}` for one-or-more) and `dest_dir` (relative to your **Content Root**) compile into the exporter's `path_patterns`/`anim_path_patterns` regex on save - the exporter itself is untouched and still only reads its own compiled keys. Validation enforces that every `{token}` used in a `dest_dir` or an `anim.{gameplay,cinematic}` entry also appears in that same row's `source_dir` (otherwise the exporter would `KeyError` deep inside its FBX-write step), that every asset class `id` is unique and slug-safe, and that both `source_dir` and `dest_dir` are non-empty.

**Library roots** (Pose / Anim) each have an "Under Source Art Root" toggle that previews the project's relative subfolder (`SourceArt/_pose` / `SourceArt/_anim` by default) resolved under YOUR Source Art Root and locks the field read-only; untick it to Browse to a custom location instead. A custom path *under* your Source Art Root is stored as a portable project subpath (it travels with the team); anywhere else becomes a per-machine override that stays on this machine only. **Blueprints Dir** works the same way with a "leave blank (factory blueprints only)" checkbox in place of a derive toggle - leaving it blank is only a warning, not an error, so it has to be an explicit choice rather than an accidental omission.

**Two tiers under the hood**: everything the editor authors except the machine paths is *project truth* (shareable; the `session.json`/`export_mapping.json` pair). The Source Art Root, Content Root, and any absolute library overrides are *machine bindings*, stored per user in `fabricator_project_configs/_user/<project>.json` and never written into the shared pair - teammates with different drive letters each bind their own roots. Multi-user / studio setup (a shared configs root, per-machine bindings) is a supported configuration - contact FabricatorStudio. Machine bindings also have a dedicated home: the [Settings](settings.md) tool (left-click the toolbar gear) binds any project on this machine without opening the project editor, which is the way to go on shared or read-only configs roots.

**Save gating**: `config_validation.validate_config()` runs on every field change and again right before Save; any `severity="error"` issue (bad unit/fps token, playback start/end set only one of the pair or out of order, empty/duplicate asset-class id, an unresolvable placeholder, a missing or empty FBX preset type, a blank required prefix, a name that collides with another project's slug) disables Save and lists itself in the VALIDATION panel. Warnings (an unrecognized `FBXExport*` key passed through as-is, a Source Art / Content Root that overlaps another bound project's, a blank blueprints location) show in the same panel but never block the write. Both machine roots are required and must be absolute paths.

**Scaffold** (post-save, skippable) offers exactly the directories your config implies - each asset class's literal `source_dir` prefix up to its first placeholder, plus Pose/Anim Studio roots and Blueprints Dir if set - and creates only the ones you check, `mkdir(parents=True, exist_ok=True)`, nothing speculative and no filler files.

**Apply & Activate** is the one action that both applies `session.json` to the live Maya session (units, camera clips, grid, playback, undo depth, FBX plugin load) *and* sets this project as the toolbar's active project, keeping those two name-based "active project" stores in sync. It does **not** change which project's `export_mapping.json` a given scene resolves to at export time - that always comes purely from matching the open scene's file path against each bound project's **Source Art Root**, independent of anything marked "active" here.

**Duplicate** copies a project's authored config under a new name through the same create-and-validate path as New (so it can't collide with anything), and **Delete** is a soft delete - it moves the project's folder to `fabricator_project_configs/_trash/<slug>_<timestamp>/`, never a hard removal.

## Gotchas
- The machine roots are validated only as "non-empty and absolute" - the tool does not check that the folders actually exist on disk. In practice the fields are read-only and can only be set via the Browse buttons (which only let you pick a real folder), so an empty path in practice means the project is not yet bound on this machine.
- **Migrating from a single-root config**: older projects (one `project_root`) keep working untouched - the old root seeds BOTH machine roots automatically on first read, and the pair upgrades on your first Save. Exports resolve identically before and after.
- A root that overlaps another saved project's is only a warning, not a block - useful right after Duplicate (both configs point at the same tree until you edit one), but it will not stop you from accidentally routing two unrelated projects at the same folder.
- An unrecognized `fbx_presets.<type>.<key>` (a typo'd `FBXExport*` option) is a warning, not an error - it saves and is passed straight through to the raw MEL export call, so a typo can still silently no-op at export time; check the VALIDATION panel's warnings, not just its errors.
- Renaming a project to a name whose slug differs from the current folder is rejected outright by Edit; the fix path is Duplicate under the new name, then Delete the old one, not a direct rename.
- On a shared/read-only `FABRICATOR_PROJECT_CONFIGS` root (a network share or an unopened Perforce workspace), template auto-seed/migration is skipped silently rather than erroring on every artist's first launch; any Save/Delete against a read-only target raises an actionable "check it out and retry" message instead of a raw permission error.
- Only `_unreal5` currently ships without an `"_status"` marker (i.e. vetted). `_unity` and `_godot` both validate clean and carry a full asset-class/FBX-preset set already, but are still labeled `"_status": "experimental"` in their own `export_mapping.json` pending Adrian's manual export/import round-trip in each engine - re-check that field yourself before treating a Unity or Godot project as production-proven, since the tool surfaces no in-UI badge for it today.

## Troubleshooting
**Save button stays disabled.** - One or more errors are listed in the VALIDATION panel (expand it if collapsed). Fix every red line; warnings (non-red) don't block Save.

**"Renaming to '...' would move the identity folder from '...' to '...'."** - Editing Name changed its derived slug. Use Duplicate to create a project under the new name, then delete the old one if it's no longer needed.

**"Project '...' already exists at ..." (FileExistsError).** - Two projects derived the same folder slug and a create raced past the validator's own collision check. Pick a name that produces a different slug.

**"Cannot write ... it looks read-only (likely checked into Perforce and not checked out)."** - The target `session.json`/`export_mapping.json` (or its parent folder) is read-only. Check it out in source control and retry Save/Delete.

**A brand-new engine template (or Generic) won't validate.** - `fbx_presets.static_mesh` / `.skeletal_mesh` / `.animation` must each be non-empty, and `asset_classes` must contain at least one entry - Generic ships with both empty on purpose as a blank starting point.

**Apply & Activate didn't change where an already-open scene exports to.** - By design: export destination is resolved purely from the scene's own file path against each bound project's Source Art Root, never from whichever project is "active." Save the scene under the right project's Source Art Root instead.
